# **UD4 - Fondamenti di Linux e terminale**

Questa lezione parte dallo snapshot `02-ssri-seed-labsetup-imported` della VM `Ubuntu-SSRI-Laboratorio`: Ubuntu 26.04 è installato, VirtualBox Guest Additions funzionano, la clipboard è bidirezionale, la cartella condivisa `VM_Shared` è montata, gli strumenti di base sono installati e i sorgenti SEED sono stati copiati in `~/ssri-lab`.

Il suo obiettivo non è insegnare C, né anticipare gli attacchi Set-UID: serve a costruire il lessico operativo minimo per muoversi su Linux da terminale, compilare, ispezionare, modificare file, capire i messaggi d'errore, usare manuali e lavorare in modo riproducibile.

Collegamenti: [L0 - Setup moderno del laboratorio VM](L0%20-%20Setup%20moderno%20del%20laboratorio%20VM.md), [L1 - Controllo degli accessi in Linux - laboratorio](L1%20-%20Controllo%20degli%20accessi%20in%20Linux%20-%20laboratorio.md), [M3/UD3/L2 - Controllo degli accessi in Linux](../UD3/L2%20-%20Controllo%20degli%20accessi%20in%20Linux.md).

### **1. Punto di partenza: snapshot giusto e assetto della VM**

Prima di fare esercizi distruttivi, la VM deve partire dallo snapshot corretto. Nel nostro caso la catena snapshot è:

```text
00-clean-ubuntu-26.04-vbox-ready
01-ssri-tools-installed
02-ssri-seed-labsetup-imported
```

Lo snapshot `00` contiene Ubuntu installato, aggiornato e integrato con VirtualBox. Lo snapshot `01` aggiunge compilatori e strumenti da laboratorio. Lo snapshot `02` aggiunge i sorgenti SEED copiati e compilati in `~/ssri-lab/setuid`.

> 📌 Per studiare e svolgere i lab conviene partire da `02`. Prima di modifiche rischiose come Set-UID root, cambio di `/bin/sh`, esperimenti su `/etc/zzz` o manipolazioni di `PATH`, crea uno snapshot ulteriore o assicurati di poter tornare a `02`.

#### **1.1. Perché gli snapshot contano**

Gli esercizi di sicurezza sono diversi dalla programmazione ordinaria: spesso il punto è proprio alterare il sistema. Un errore può lasciare:

1. shell di sistema cambiate;
2. file root-owned creati a mano;
3. permessi Set-UID attivati;
4. variabili d'ambiente persistenti nel profilo;
5. pacchetti o configurazioni di rete modificati.

Lo snapshot è il modo pragmatico per separare apprendimento ed esperimento. Invece di "ripulire a mano" un sistema compromesso da prove, si ripristina uno stato noto.

> ⚠️ Non usare la VM come se fosse il tuo sistema personale. È un banco di prova: va bene romperla, purché tu possa tornare indietro.

### **2. Preparare l'interfaccia: terminale sempre raggiungibile**

Ubuntu permette di fare quasi tutto da GUI, ma i lab del corso sono molto più controllabili da terminale. Il primo gesto pratico è rendere il terminale sempre disponibile.

#### **2.1. Aprire il terminale**

Modi comuni:

1. scorciatoia `Ctrl+Alt+T`;
2. icona Terminale/Ptyxis nel dock;
3. ricerca applicazioni, digitando `terminal`.

Nel nostro ambiente Ubuntu 26.04 potresti vedere `Ptyxis` come terminale predefinito. Per i lab non cambia: è una finestra che avvia una shell, tipicamente `bash`.

#### **2.2. Pinnare il terminale sul dock**

Procedura:

1. apri il terminale;
2. fai click destro sull'icona del terminale nel dock;
3. scegli **Aggiungi ai preferiti**.

Da quel momento il terminale resta nel dock anche dopo la chiusura.

> 💡 La CLI non è "più hacker" perché è esteticamente più scura: è preferita perché rende le azioni ripetibili, copiabili, salvabili in appunti, verificabili e automatizzabili.

#### **2.3. Massimizzare e lavorare a schermo pieno**

In VirtualBox:

```text
Ctrl destro + F
```

attiva/disattiva il full screen. Il resize automatico del guest deve essere abilitato da:

```text
Visualizza > Ridimensiona automaticamente lo schermo guest
```

Nel terminale:

1. `Ctrl+Shift++` aumenta lo zoom;
2. `Ctrl+-` spesso riduce lo zoom;
3. `Ctrl+Shift+C` copia;
4. `Ctrl+Shift+V` incolla.

> ⚠️ In terminale `Ctrl+C` non copia: interrompe il processo in foreground. Per copiare serve `Ctrl+Shift+C`.

### **3. Capire cosa si sta guardando: shell, prompt e comandi**

Una finestra terminale esegue una **shell**. Nel nostro caso, salvo modifiche, la shell è `bash`.

Puoi verificarlo con:

```bash
echo $SHELL
```

Il prompt:

```bash
seed@ubuntu-ssri:~/ssri-lab/setuid$
```

si legge così:

| Parte | Significato |
|---|---|
| `seed` | utente corrente |
| `ubuntu-ssri` | nome host della VM |
| `~/ssri-lab/setuid` | directory corrente |
| `$` | shell non privilegiata |

Se il prompt termina con `#`, di solito sei root o in una shell privilegiata.

> 📌 Il prompt è un indicatore di contesto. Prima di lanciare comandi distruttivi, controlla sempre utente e directory corrente.

#### **3.1. Comando, opzioni, argomenti**

Un comando Linux tipico ha questa forma:

```bash
comando -opzioni argomenti
```

Esempi:

```bash
ls -l ~/ssri-lab
gcc myenv.c -o myenv
sudo apt install -y nmap
```

In `gcc myenv.c -o myenv`:

1. `gcc` è il programma;
2. `myenv.c` è un argomento input;
3. `-o` è un'opzione;
4. `myenv` è l'argomento dell'opzione `-o`, cioè il nome dell'eseguibile prodotto.

#### **3.2. Case sensitivity**

Linux distingue maiuscole e minuscole:

```text
Lab
lab
LAB
```

sono tre nomi diversi.

> ⚠️ Molti errori iniziali vengono da path scritti con maiuscole/minuscole sbagliate. Se un file "non esiste", verifica prima il nome esatto con `ls`.

### **4. Orientarsi nel filesystem**

Linux usa un albero unico che parte da `/`, la root del filesystem. Non ci sono lettere di unità come `C:` o `D:` nel modello UNIX.

Percorsi importanti:

| Percorso | Uso |
|---|---|
| `/` | radice del filesystem |
| `/home/seed` | home dell'utente `seed` |
| `~` | abbreviazione della home dell'utente corrente |
| `/etc` | configurazioni di sistema |
| `/bin`, `/usr/bin` | programmi eseguibili |
| `/tmp` | file temporanei |
| `/media/sf_VM_Shared` | cartella condivisa VirtualBox |

#### **4.1. Dove siamo**

```bash
pwd
```

stampa la directory corrente.

```bash
whoami
hostname
id
```

mostrano rispettivamente utente, nome macchina e identità/gruppi.

#### **4.2. Cambiare directory**

```bash
cd ~
cd ~/ssri-lab
cd ..
cd -
```

Significati:

| Comando | Effetto |
|---|---|
| `cd ~` | torna nella home |
| `cd ~/ssri-lab` | entra nella directory lab |
| `cd ..` | risale di un livello |
| `cd -` | torna alla directory precedente |

#### **4.3. Listare file**

```bash
ls
ls -l
ls -la
ls -lh
```

Opzioni utili:

| Opzione | Effetto |
|---|---|
| `-l` | formato lungo con permessi, owner, gruppo, dimensione |
| `-a` | mostra anche file nascosti, quelli che iniziano con `.` |
| `-h` | dimensioni leggibili, ad esempio KB/MB |

Per i lab Set-UID useremo spesso:

```bash
ls -l
```

perché mostra permessi, proprietario e bit speciali.

> 📌 In Linux i file nascosti non hanno attributo speciale: per convenzione iniziano con punto, ad esempio `.bashrc`.

### **5. Creare, copiare, spostare e cancellare**

#### **5.1. Creare directory**

```bash
mkdir prova
mkdir -p ~/ssri-lab/{setuid,env,pcap,tools,notes}
```

`-p` crea anche i genitori mancanti e non dà errore se la directory esiste già.

#### **5.2. Copiare**

```bash
cp sorgente destinazione
cp file.c ~/ssri-lab/setuid/
cp -r cartella altra_cartella
```

`-r` copia ricorsivamente una directory.

#### **5.3. Spostare o rinominare**

```bash
mv vecchio_nome nuovo_nome
mv file.txt ~/ssri-lab/notes/
```

`mv` serve sia per spostare sia per rinominare.

#### **5.4. Cancellare**

```bash
rm file.txt
rm -r cartella
```

> ⚠️ `rm` non manda nel cestino. Da terminale, la cancellazione è normalmente definitiva. Non usare mai `sudo rm -r` se non sai esattamente quale path stai cancellando.

#### **5.5. Leggere file**

```bash
cat file.txt
less file.txt
head file.txt
tail file.txt
tail -f log.txt
```

| Comando | Quando usarlo |
|---|---|
| `cat` | file brevi |
| `less` | file lunghi, navigabile |
| `head` | prime righe |
| `tail` | ultime righe |
| `tail -f` | seguire log in tempo reale |

In `less`:

1. `q` esce;
2. `/testo` cerca;
3. `n` passa al risultato successivo;
4. `g` va all'inizio;
5. `G` va alla fine.

### **6. Tab completion, history e correzione errori**

#### **6.1. Tab completion**

Premendo `Tab`, la shell completa nomi di file, directory e comandi.

Esempio:

```bash
cd ~/ssri<Tab>
```

può diventare:

```bash
cd ~/ssri-lab/
```

Se ci sono più possibilità, premi `Tab` due volte per vederle.

> 💡 I professionisti digitano meno di quanto sembri: usano completamento, history e copia consapevole.

#### **6.2. History**

```bash
history
```

Frecce:

1. `Freccia su`: comando precedente;
2. `Freccia giù`: comando successivo.

Ricerca interattiva:

```text
Ctrl+R
```

poi digita una parte del comando. Premi `Enter` per eseguirlo o frecce per modificarlo.

#### **6.3. Interrompere un comando**

```text
Ctrl+C
```

invia un segnale di interruzione al processo in foreground.

```text
Ctrl+D
```

chiude input o termina una shell quando non c'è testo da inviare.

```text
Ctrl+L
```

pulisce la schermata, equivalente a `clear`.

### **7. Editare da terminale con `nano`**

Per iniziare, `nano` è l'editor CLI più semplice. Non è potente come Vim, ma è sufficiente per modificare sorgenti e note durante i lab.

Aprire un file:

```bash
nano myenv.c
```

Comandi essenziali:

| Shortcut | Effetto |
|---|---|
| `Ctrl+O` | salva, "Write Out" |
| `Enter` dopo `Ctrl+O` | conferma il nome file |
| `Ctrl+X` | esce |
| `Ctrl+K` | taglia la riga corrente |
| `Ctrl+U` | incolla la riga tagliata |
| `Ctrl+W` | cerca testo |
| `Ctrl+\` | cerca e sostituisce |
| `Alt+U` | undo, se supportato |
| `Alt+E` | redo, se supportato |

In basso `nano` mostra `^O`, `^X`, `^W`: il simbolo `^` significa `Ctrl`.

> 📌 `Ctrl+O`, `Enter`, `Ctrl+X` è la sequenza base: salva, conferma, esci.

#### **7.1. Evitare l'errore classico**

Se apri:

```bash
nano myenv.c
```

modifichi il file, poi premi solo `Ctrl+X`, `nano` chiede se salvare. Rispondere `N` perde le modifiche.

Sequenza sicura:

```text
Ctrl+O
Enter
Ctrl+X
```

#### **7.2. Quando usare VS Code e quando no**

Puoi programmare in VS Code su Windows, ma per questi lab conviene modificare ed eseguire dentro Ubuntu perché:

1. permessi e proprietari Linux sono reali;
2. Set-UID, `chown`, `chmod`, `/etc`, `PATH` e loader dinamico vanno testati nel guest;
3. la shared folder può alterare proprietà e bit di permesso;
4. gli output dei comandi sono parte dello studio.

> ⚠️ Non compilare/eseguire i lab Set-UID dentro `/media/sf_VM_Shared`. Usa la shared folder solo per trasferire file; lavora in `~/ssri-lab`.

### **8. Ottenere aiuto: `man`, `--help`, `type`, `which`**

#### **8.1. Manuali**

```bash

```

Le sezioni di `man` contano:

| Sezione | Contenuto |
|---|---|

Per uscire da `man`, premi `q`.

> 📌 `man 2 execve` documenta la system call; `man 3 system` documenta la funzione C di libreria. Questa distinzione è cruciale nei lab.

#### **8.2. Help rapido**


```bash

command -v python3
```

`type` è spesso più informativo di `which`, perché distingue eseguibili, alias, funzioni e built-in della shell.

### **9. Pacchetti, aggiornamenti e `sudo`**

Ubuntu usa `apt` per gestire pacchetti.

#### **9.1. Aggiornare indice e pacchetti**

```bash
sudo apt update
sudo apt full-upgrade -y
```

`apt update` aggiorna l'indice dei pacchetti disponibili. Non installa aggiornamenti. `apt full-upgrade` installa gli aggiornamenti e può aggiungere/rimuovere pacchetti se necessario.

#### **9.2. Installare pacchetti**

```bash
sudo apt install -y build-essential gdb valgrind strace ltrace
```

`-y` risponde sì automaticamente alle conferme.

#### **9.3. Cercare pacchetti**

```bash
apt search nome
apt show nome
```

#### **9.4. `sudo`**

`sudo` esegue un comando con privilegi amministrativi. La password richiesta è quella dell'utente `seed`, cioè `dees` nella nostra VM.

```bash
sudo comando
```

> ⚠️ Non usare `sudo` "perché così funziona". Se un comando fallisce senza `sudo`, chiediti quale permesso manca e perché. Nei lab, distinguere utente normale e privilegi root è parte dell'esercizio.

### **10. Permessi essenziali prima del Set-UID**

La teoria completa è in M3/UD3 e nelle lezioni successive. Qui serve solo saper leggere `ls -l`.

Esempio:

```text
-rwxr-xr-- 1 seed seed 16008 Jul 8 00:05 myenv
```

Si legge:

| Campo | Significato |
|---|---|
| `-` | file ordinario |
| `rwx` | owner può leggere, scrivere, eseguire |
| `r-x` | gruppo può leggere ed eseguire |
| `r--` | altri possono solo leggere |
| `seed seed` | proprietario e gruppo |

#### **10.1. Rendere eseguibile**

```bash
chmod +x script.sh
```

#### **10.2. Cambiare permessi in ottale**

```bash
chmod 755 programma
chmod 644 file.txt
```

Valori:

| Valore | Significato |
|---|---|
| `4` | read |
| `2` | write |
| `1` | execute |

Quindi `7 = 4+2+1 = rwx`, `5 = 4+1 = r-x`, `4 = r--`.

#### **10.3. Proprietario**

```bash
sudo chown root:root programma
```

Questo cambia owner e gruppo. Nei lab Set-UID sarà essenziale, ma va usato solo nella VM.

> 📌 Prima di attivare Set-UID, devi già saper leggere owner, gruppo e bit di esecuzione con `ls -l`.

### **11. Redirezioni, pipe e file di output**

La CLI diventa potente quando puoi collegare comandi.

#### **11.1. Redirezione output**

```bash
./myprintenv > child.env
./myprintenv >> all.env
```

| Operatore | Effetto |
|---|---|
| `>` | sovrascrive il file |
| `>>` | aggiunge in fondo |

> ⚠️ `>` distrugge il contenuto precedente del file. Se vuoi accumulare output, usa `>>`.

#### **11.2. Redirezione errori**

```bash
comando 2> error.log
comando > output.log 2> error.log
comando > all.log 2>&1
```

Linux distingue:

1. standard output, canale `1`;
2. standard error, canale `2`.

#### **11.3. Pipe**

```bash
./myenv | head
./myenv | grep PATH
history | grep gcc
ls -l | less
```

La pipe `|` passa l'output di un comando come input al successivo.

#### **11.4. `grep`**

```bash
grep PATH parent.env
grep -n "execve" *.c
grep -R "system(" ~/ssri-lab
```

Opzioni:

| Opzione | Effetto |
|---|---|
| `-n` | mostra numero di riga |
| `-R` | cerca ricorsivamente |
| `-i` | ignora maiuscole/minuscole |

### **12. Compilare ed eseguire C su Linux**

Hai già competenze C; qui serve tradurle nel flusso CLI Linux.

#### **12.1. Compilazione base**

```bash
gcc myenv.c -o myenv
./myenv
```

Perché `./myenv` e non solo `myenv`?

La directory corrente di solito non è nel `PATH`. Scrivendo `./myenv` dici alla shell: esegui il file `myenv` che si trova nella directory corrente.

> 📌 `./programma` è una delle prime differenze pratiche rispetto a Windows: su Linux non si esegue implicitamente dalla directory corrente.

#### **12.2. Warning utili**

Per studio serio:

```bash
gcc -Wall -Wextra -g myenv.c -o myenv
```

| Opzione | Effetto |
|---|---|
| `-Wall` | abilita molti warning |
| `-Wextra` | abilita warning aggiuntivi |
| `-g` | include simboli per debug con `gdb` |

#### **12.3. Debug minimo**

```bash
gdb ./myenv
```

Dentro `gdb`:

```text
run
break main
next
step
print variabile
quit
```

Per ora basta sapere che `-g` prepara l'eseguibile al debug.

#### **12.4. Valgrind**

```bash
valgrind ./programma
```

Serve per memory leak e accessi invalidi. Non sarà centrale nei lab Set-UID, ma è utile per C.

### **18. Errori comuni e diagnosi**

#### **18.1. `command not found`**

Cause:

1. pacchetto non installato;
2. errore di battitura;
3. programma nella directory corrente ma lanciato senza `./`;
4. `PATH` non contiene la directory.

Diagnosi:

```bash
type comando
which comando
ls -l ./programma
```

#### **18.2. `Permission denied`**

Cause:

1. file non eseguibile;
2. directory senza permesso `x`;
3. operazione richiede root;
4. file su shared folder con permessi strani.

Diagnosi:

```bash
ls -l file
id
pwd
```

Correzioni possibili:

```bash
chmod +x programma
sudo comando
```

ma solo dopo aver capito il motivo.

#### **18.3. `No such file or directory`**

Cause:

1. path sbagliato;
2. maiuscole/minuscole;
3. directory corrente diversa da quella pensata;
4. file non copiato.

Diagnosi:

```bash
pwd
ls
find ~/ssri-lab -name "nome*"
```

#### **18.4. Terminale "bloccato"**

Prova:

1. `Ctrl+C`;
2. `q` se sei in `less`, `man`, `top`;
3. `Ctrl+D` se un comando aspetta EOF;
4. chiudere e riaprire il terminale se è solo una shell di lavoro.

| Aggiorna indice apt | `sudo apt update` |
| Installa pacchetto | `sudo apt install nome` |

### **20. Sequenza consigliata prima di ogni lab**

Prima di un esercizio pratico:


Se l'esercizio modifica privilegi o shell:

1. controlla snapshot VirtualBox;
2. lavora in directory nativa Linux;
3. scrivi comandi in un file note;
4. evita di lasciare variabili alterate senza sapere come rimuoverle;
5. a fine esercizio ripristina o crea snapshot.
